Foundations / 01

Start here

You want to explain identity mechanisms across platforms, not memorize a cloud console. This guide starts with one question: How can a service safely decide whether to accept a request? OAuth, API keys and tokens solve different parts of that problem.

Use the first six sections for a first pass. Then read refresh and the worker example. The final sections are for interview practice and optional depth. Reading is not a mastery checkpoint; explaining a mechanism in your own words is.

Identity and permissions→Credentials and tokens→One request→Expiry and many workers

All names, token versions and durations in examples are fictional. No real credentials, production code or provider-specific quota claims appear here. Implementation patterns are labeled separately from protocol concepts.

Foundations / 02

1 Identity authentication and authorization

Identity

A representation of a person or workload. A principal is an entity the system can recognize and grant permissions to. An identifier names it; a credential helps prove a claim about it.

Authentication · AuthN

Establish who or what is making a claim. A password, passkey or certificate can be evidence. MFA combines independent factors; it does not itself decide which data may be read.

Authorization · AuthZ

Decide whether this actor can perform this action on this resource. Knowing someone’s identity does not imply that they may read every customer’s records.

Example: An employee signs in successfully, but cannot delete another team’s project. Authentication succeeded; authorization denied the operation. A backend service also needs permissions, even though no person is currently typing a password.

Single sign-on reuses a trusted identity session across applications. It does not mean all applications receive the same permissions.

Imagine ImportApp copies a customer’s contacts from ExampleCRM.

An API key’s meaning varies by provider. Some identify a project for quota; others authorize actions for an account or service. Keys may have scopes, restrictions, expiry and rotation. Do not say “API keys always last forever” or “API keys always identify a user.” OAuth defines an authorization framework; “API key” does not specify one universal lifecycle.

Access tokens are often short-lived, while refresh tokens may last longer. Exact lifetimes and whether refresh tokens are issued are provider and flow decisions. An ID token is not a general-purpose API credential.

Foundations / 05

4 OAuth is not the same as login

OAuth 2.0 is an authorization framework. A common use is allowing ImportApp limited access to a customer’s CRM records without giving ImportApp the customer’s password. OAuth also supports a service acting on its own behalf.

OpenID Connect · OIDC adds an authentication layer. It defines how a client obtains and validates an ID token describing user authentication. “Sign in with…” often uses OIDC on top of OAuth.

Connect my CRM

The central question is: may ImportApp read these contacts? That is delegated API access.

Sign in to ImportApp

The central question is: which user is signing in? That is authentication. ImportApp still applies its own authorization rules afterward.

The same journey may involve both, which is why they look like one operation to a user. Keep their purposes separate in an interview.

Sources: [2], [3].

Follow the credentials / 06

5 A concrete authorization code flow

This is the conceptual modern pattern for a user-facing integration. Use a mature library in production, not a hand-built protocol implementation.

  1. Start a connection. ImportApp redirects the browser to the provider, requesting limited access and specifying its registered callback. It prepares request-binding protections.
  2. The provider handles the user. It authenticates the customer if needed and obtains authorization according to its policies. Prior consent or an organization’s policy may avoid a fresh consent prompt.
  3. Return a short-lived code. The browser returns to the callback with an authorization code. This is an intermediate credential, not the access token used for data requests.
  4. Exchange the code. ImportApp sends it to the token endpoint with the PKCE verifier and any required client authentication.
  5. Receive credentials. The result includes an access token and metadata. A refresh token may be issued. With OIDC, an ID token is also part of the authentication flow.
  6. Call the API. ImportApp sends the access token to the intended contacts API, which validates it and authorizes the request.

What PKCE adds

Pronounced “pixie,” PKCE links the code exchange to the client instance that started the flow. The client creates a random verifier and sends a derived challenge at the start. At exchange time, it proves possession of the verifier. A stolen authorization code alone should not be sufficient to redeem it.

PKCE does not encrypt the token, replace API permissions, or make a browser capable of keeping a client secret. The exact redirect, state and OIDC nonce checks belong to a vetted library and the chosen flow.

Sources: [8], [9].

Follow the credentials / 07

6 What happens on an API request

For a bearer-token API, the client commonly sends an HTTPS request with Authorization: Bearer <access-token>. “Bearer” means possession is sufficient to use the credential, subject to validation; protect it from theft.

The API asks: Is this token valid for me? Is the requested action allowed? Is this record within the caller’s permitted tenant or ownership boundary? A token with permission to read contacts must not bypass record-level restrictions.

The three boundaries to remember

  • Issuer: who issued it, and do we trust that issuer?
  • Audience: which API or client is meant to accept it?
  • Scope or permission: what access was granted?

Expiry adds a time boundary. A valid signature alone is insufficient: an unexpired token issued for API A is not automatically acceptable to API B. Clients should use returned metadata for expiry rather than depend on decoding a provider’s access-token internals.

Sources: [5], [10], [11].

Follow the credentials / 08

7 JWT opaque tokens and validation

Token purpose and token format are separate. JWT is a format for claims, not a replacement for OAuth. An access token may be JWT-shaped or opaque. OIDC ID tokens use JWT.

JWT

A signed JWT carries claims and integrity protection. The familiar signed form has header, payload and signature segments. Encoding is not encryption: readable payloads must not be treated as secret storage. Encrypted JWT forms also exist.

Opaque token

A string whose internal meaning is not available to the client. The API can use an authorization-server lookup or supported introspection endpoint to determine its active status and authorization context.

For JWT access tokens, the API must validate trusted keys and permitted algorithms, issuer, audience, relevant times and token type, then enforce permissions. A decoded payload is only untrusted data until validation succeeds. Use established validation libraries; do not trust a token’s own claims to choose arbitrary verification behavior.

Local JWT verification reduces per-request dependence on the issuer. Online status checks can improve awareness of revocation but add dependency and latency. Caching those checks introduces a freshness trade-off. This is a design choice, not “JWT always wins.”

Sources: [12], [13], [14].

Follow the credentials / 09

8 Expiry and refresh with one worker

Suppose a fictional access token lasts 30 minutes and an import needs an hour. A worker does not ask the user to sign in for every page.

  1. Store the expiry metadata when credentials are obtained.
  2. Before expiry, ask the token manager for a usable token. A small configurable margin allows for clock differences and request time.
  3. If renewal is needed and a refresh token is available, send that refresh token to the provider’s token endpoint.
  4. The provider validates the refresh grant and any client-authentication requirements, then returns a new access token if allowed.
  5. Persist updated credentials safely and continue. If a new refresh token is returned, handle it according to the provider’s rules.

The refresh token is not a local algorithm for manufacturing an access token. The provider issues the replacement. Refresh can fail because access was revoked, the credential expired, or a policy requires interaction again.

Provider differences matter: rotation may invalidate the previous refresh token or have other reuse semantics. Microsoft’s documented behavior must not be generalized to every identity provider. Read the integration’s actual contract.

Sources: [6], [15].

Distributed systems / 10

9 Ten workers and one expired token

Application design pattern, not a component required by OAuth

Assume the API error indicates an expired or otherwise refreshable access token. All ten workers serve the same customer connection and hold token version 7. “Version” is metadata maintained by our application, not an OAuth claim we assume exists.

↓
Current version is v8?Yes: use v8 and retry the safe read once
↓ otherwise

Why not let every worker refresh?

Ten simultaneous failures can create ten competing refresh calls. Besides unnecessary traffic, rotated refresh tokens can make those calls race. A single in-process lock protects only one process, not ten replicas.

What each component owns

  • Token manager: a logical interface that returns a usable token and coordinates renewal. It can have multiple replicas.
  • Protected durable store: retains the current credential set, including refresh token where applicable, expiry and application version.
  • Shared cache: gives workers a fast view of usable access credentials. Eviction must not destroy the only recoverable connection state.
  • Per-connection lease: gives one manager a bounded opportunity to renew. Unrelated customer connections need not block one another.
  • Conditional write: compare the expected stored version before replacing it, so a stale manager cannot overwrite newer credentials.

After acquiring the lease, reread the record: another manager may have refreshed while this one waited. Commit the access token, expiry and any rotated refresh token consistently before advertising the new version. Isolate keys by provider, connection and relevant audience/scope so one customer never receives another’s credentials.

Important boundary: a lease plus a version check is useful coordination, not magical exactly-once execution at an external provider. A stalled owner whose lease expires may still have a request in flight. Prevent uncontrolled overlapping refreshes, reject stale writes, and reconcile uncertain outcomes using provider-specific behavior.

Distributed systems / 12

11 The refresh response was lost

Optional reliability depth

Suppose the provider accepts refresh token R7, invalidates it, and creates R8. The response is lost before your system saves R8. Your database still contains R7.

Blindly repeating R7 might fail or trigger refresh-token reuse detection. Keeping R7 in a durable database did not make this two-system operation atomic. A distributed lock did not make the response arrive.

A robust integration distinguishes known failure from unknown outcome. Use documented grace periods, reuse behavior or recovery mechanisms if the provider offers them. If recovery is impossible, pause the connection with its data checkpoint intact and require reauthorization. Do not promise universal automatic recovery.

Rotation helps detect stolen refresh-token reuse; it also requires careful client persistence. This is why “just cache the token” is an incomplete answer.

Sources: [15].

Explain and review / 13

12 What if there is no user

In the client-credentials flow, a confidential service authenticates as itself and requests an access token for permissions assigned to that service. There is no user delegation or user-consent screen in that exchange.

The service can authenticate with a supported secret, certificate or federated workload assertion. A public browser or distributed mobile app cannot reliably keep a shared client secret confidential.

When the access token expires, the service normally obtains another using its own credentials. A refresh token is generally unnecessary and should not be assumed. The OAuth client-credentials token response should not include one; provider documentation governs supported behavior.

Interview contrast: “A customer connecting their CRM account usually involves delegated authorization. A backend accessing its own authorized service resources may use client credentials. I choose based on whose authority the integration needs, not merely whether it runs in the background.”

Sources: [17].

Explain and review / 14

13 Sessions logout and revocation

A web app may establish its own session after verifying an OIDC login. The browser then carries an application cookie; the server can map it to session state. The provider’s sign-in session, the app’s session and API tokens have different lifetimes.

Cookies are a transport/storage mechanism, not proof that the system uses or avoids OAuth. Secure, HttpOnly and appropriate SameSite settings help protect browser sessions, alongside CSRF defenses and application security.

Logging out of ImportApp can end its local session without automatically invalidating every token at the CRM provider. Revoking a grant or refresh token can prevent future renewal, but already-issued access tokens may remain usable until expiry or a supported revocation check takes effect.

That creates a trade-off: short token lifetimes limit the exposure window but increase renewal activity. An API requiring immediate revocation needs an explicit enforcement mechanism, not merely a JWT with an expiry timestamp.

Sources: [7], [18].

Explain and review / 15

14 Practice explaining the mechanisms

Try answering aloud before opening each explanation. These are practice responses, not claims about your experience.

What is the difference between authentication and authorization?

Authentication establishes who or what the actor is. Authorization decides whether that actor can perform a particular action on a particular resource. A successful login does not grant access to every record.

Why use OAuth instead of asking for the customer’s password?

OAuth allows an application to obtain limited API access under a grant without taking possession of the user’s password. The provider controls token issuance and access policy. The application still has to protect its tokens.

Access token versus refresh token?

The access token goes to the resource API. The refresh token goes to the authorization server to request replacement access credentials when permitted. Neither belongs in logs or queue payloads.

Is OAuth a login protocol?

OAuth defines authorization. OIDC adds standardized user authentication on top, including an ID token intended for the client. A product may combine both in one sign-in experience.

What happens when one worker gets a 401?

I compare the token version it used with the latest shared credentials. If a newer token exists, I retry the safe request with that token. If the error indicates an expired or otherwise refreshable access token, I coordinate one refresh per connection, persist the new credential set safely, and let the other workers reuse it. Persistent authorization failures stop the retry loop.

Why is a distributed cache not enough?

A cache shares values but does not automatically coordinate refresh ownership, protect rotated refresh-token updates, or recover uncertain provider outcomes. I need explicit renewal coordination and durable state appropriate to the integration.

Does adding workers require separate OAuth tokens?

Not necessarily. Workers operating for the same authorized connection can reuse an appropriate access token. Separate customers, permissions or audiences may require separate credentials. Rate-limit scope is a separate provider rule.

Can we use an ID token to call a protected API?

Not as a substitute for the access token that API expects. The ID token is intended for the client’s authentication context; the access token is intended for the resource server.

Does a signed JWT hide its data?

No. Signing protects integrity and helps establish provenance, not confidentiality. Ordinary signed JWT payloads are readable. Encryption is a distinct mechanism.

How would you describe the overall design in 45 seconds?

“I separate authorization from the worker pipeline. Each connection has a credential provider that supports the configured authentication method. Workers request usable access credentials without handling refresh logic independently. For OAuth, the manager tracks expiry, coordinates refresh across replicas, and persists rotated credentials safely. On a 401, a worker first checks for a newer token. Authentication failures, permission failures and rate limits have different handling. If access must be reauthorized, I pause only that connection and preserve its checkpoint.”

Explain and review / 16

15 Check your understanding

Each exercise is a fictional failure scenario. Explain the reason, not just the answer.

A token is unexpired and signed by a trusted provider. Is it safe for any API to accept it?

No. The API must check its intended audience, token type and applicable authorization as well as signature and time checks.

A worker gets 429. Should it refresh the token?

No. Throttling is not solved by renewing credentials. Slow affected requests according to the provider’s limit and retry guidance.

A cache entry disappeared. Should we ask the customer to log in immediately?

Not automatically. Reconstruct the connection’s usable credentials from protected durable state where available. A cache miss and a revoked grant are different events.

A manager loses its lease after sending a refresh request. Can a new manager assume nothing happened?

No. The provider may already have accepted the request. Local lease ownership does not reveal a remote outcome. Treat it as an integration-specific uncertainty and avoid blind competing refreshes.

The user closed their browser. Must the background import stop?

Not solely because the browser closed. If a valid grant and suitable credentials permit background access, the server can continue. Revocation, expiry or provider policy can still require renewed interaction.

A practical learning sequence

  1. Draw the client, authorization server and resource server. Point to where each token goes.
  2. Explain a normal API request without using the word “cache.”
  3. Add expiry and explain what the provider, rather than your code, does.
  4. Add ten workers and explain why a single logical refresh owner is useful.
  5. Break the network after refresh and identify what remains unknown.

Readiness checkpoint: You can explain all five steps without assuming Microsoft-specific token lifetimes, account setup or claim names. You do not need to memorize endpoint parameters to reach that level.

16 Compact glossary

Grant
The authorization basis used to obtain access credentials.
Consent
Approval of requested access, by a user or relevant administrative policy.
Scope
A named slice of requested or granted access; its exact meaning is provider-defined.
Claim
A statement in a token or identity assertion, such as issuer, subject or audience.
Subject
The entity a token’s claims describe; identify it within the issuer’s namespace.
Bearer credential
A credential usable by its possessor without a separate proof-of-possession step.
Rotation
Replacing a credential with a new one; old-credential validity depends on the protocol/provider policy.
Revocation
Invalidating a credential or authorization before its normal expiry.
Single-flight
An application pattern that makes concurrent callers share one in-flight operation.
Lease
Time-bounded ownership used to coordinate work across processes.
Compare-and-swap
A conditional state update that succeeds only if the expected version still matches.
Least privilege
Grant only the access needed for the task, rather than broad permissions “just in case.”

For advanced systems, sender-constrained tokens can bind use to a key rather than possession alone. That is useful depth later; ordinary bearer-token handling is the right first foundation.
